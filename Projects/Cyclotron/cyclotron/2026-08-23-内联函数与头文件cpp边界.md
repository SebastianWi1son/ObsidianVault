# 对话总结：内联函数与头文件/cpp 边界（2026-08-23）

> 纯事实总结。背景：cyclotron foc 库——transforms 头文件 inline 实现 vs 其他组件声明/定义分离（D10），用户追问"内联能不能写 cpp 里"
> 关联：`foc/docs/FOC_MATH_SPEC.md`（§1.5 transforms 完整实现）、`foc/docs/FOC_CORE_PSEUDOCODE.md`（§3 实现注意）

## 一、inline 函数能写 cpp 里吗

**分两种情况：**

- **情况 A（自用）**：只在某个 .cpp 内部使用的私有辅助函数，写在 cpp 里 ✅ 可以。此时 inline 等价 static（内部链接），只服务本编译单元的调用点。
- **情况 B（对外）**：声明在头文件、定义在 cpp、被多个翻译单元调用 ❌ 不行，**ODR 违反**。

**ODR 规则**：inline 函数的完整定义必须出现在每个使用它的翻译单元中。头文件只有声明，其他 .cpp 看不到定义 → 没被内联的调用点找不到符号 → 链接错误（undefined reference）。

**推论**：要对外且内联 → 定义放头文件；要放 cpp → 去掉 inline 当普通函数（外部符号链接）。

## 二、inline 的真实语义（常见误解）

- `inline` 关键字**不是"强制内联"**——它是 **ODR 豁免**：允许定义在多个翻译单元各出现一份，链接器去重
- 真正内联是编译器 -O2 自动做的：小函数定义可见就内联，大函数写了 inline 也拒绝
- 所以写 inline 的真实作用 = "让定义能安全待在头文件"（链接层面），不是性能承诺
- 附带：C++17 `inline constexpr` 变量同理（头文件安全，如 `inline constexpr float SQRT3`）

## 三、static inline vs inline

| | static inline（legacy C 风格） | inline（现代 C++） |
|---|---|---|
| 语义 | 每 TU 一份独立副本（内部链接） | 弱符号，链接器去重 |
| 代价 | 代码膨胀（每 TU 各存一份） | 无 |

现代 C++ 用裸 `inline`。

## 四、头文件实现 vs cpp 分离：判断三问

```
① 有内部状态要保护？         是 → cpp 分离（隐藏实现细节）
② 调用频率高（每 tick 多次）？是 → 头文件 inline（消除调用开销）
③ 函数小（<10 行）且数学稳定？是 → 头文件 inline（很少改，重编成本低）
```

## 五、本项目实例（两类形态共存）

| 组件 | 形态 | 理由 |
|---|---|---|
| transforms | 头文件 inline 实现 | 零状态纯函数 + 1kHz 每 tick 调 4 次 + 3-5 行小函数 |
| algo（PID/LPF/Ramp/Planner） | 声明/定义分离 | 有内部状态（integral_ 等），隐藏实现 |
| svpwm / angle_tracker / alignment / foc_core | 声明/定义分离 | 有状态或有内部逻辑；低频（每 tick 一次）；cpp 分离带来构建收益（改实现不触发全量重编） |

**D10 澄清**："声明/定义分离"约束适用于有状态组件；inline 纯函数/模板/类内定义成员函数是 C++ 标准例外，同库共存是标准实践。

**代价说明**：头文件实现 = 改头文件会触发所有包含者重编；数学稳定组件（transforms）很少改，成本可忽略。
