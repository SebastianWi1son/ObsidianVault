# 2026-08-23 Config 职责边界（D14）

## 一句话心智模型

**Config = 启动时填一次的表。** 填表的人（main/上层）只管开头一次；干活的人（tick，1000 次/秒）永远不看表；以后加新项只改表，不改任何干活流程。

## 插座模型（Config 的形态）

```cpp
struct Config { float vel_lpf_Tf; float traj_Tf; float ...; };
```

- **类型来自上游**：float/int 中性插头规格（LPF 的 Tf 就是 float）
- **语义来自下游**：vel_lpf_/traj_ 领域前缀（宿主自己起名）
- **法则：类型归上游，语义归下游**——下游不发明类型（遵守上游插头），上游不定义语义（不侵入下游领域）

## 为什么需要 Config（聚合三大价值）

1. **配置期/运行期分离**：设置一次，干活不管设置——tick 只传会变化的数据（角度/dt），不变的配置开头给一次。类比：座椅/后视镜开车前调好，开车中不再碰
2. **演进安全**：加参数 = Config 加一行字段，调用点零改动；散着传 = 改所有调用点，且顺序错 = 隐蔽 bug（把阈值传成滤波系数，行为鬼畜查不到）
3. **可读性**：`PID(0.1f, 0.05f, 0.001f, ...)` 8 个 float 记不住 vs `PIDConfig{ .kp_=..., .ki_=... }` 字段名即文档

## 归属准则（D14 正式结论）

1. **公开组件（API 面）→ 自备 Config**——即使当前 1 个参数（angle_tracker），因为 API 面演进安全优先
2. **内部原语（LPF/Ramp/SmoothPlanner）→ 构造传参，不设 Config**——内部使用，改签名成本低；1 参数建 Config 是过度设计
3. **宿主 Config 平铺转发零件参数，不嵌套零件 Config**——wheel 先例 `PIDConfig.d_filter_Tf_`；SimpleFOC 同款（LowPassFilter 构造传参）

## 易混点（三次问答沉淀）

- Config **不是**"没有语义的通用载体"——它恰恰是领域语义的载体：`vel_lpf_Tf` = "速度滤波时间常数"（领域概念），不是"LPF 的 Tf"（实现概念）。值转发给 LPF，语义在宿主侧升维
- "统一承接 spec"是聚合的**自然结果**，核心目的是聚合（配置/运行分离 + 演进安全）
- angle_tracker 建 Config 因为它是**公开组件**；LPF 不建因为它是**内部原语**——层级区分，不是双重标准
- legacy 里 `foc_motor_t.cfg` 就是同款模式（配置结构体），wheel 只是变成 C++ 构造输入 + 演进安全保证
