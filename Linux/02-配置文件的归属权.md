# 配置文件的归属权

## 一句话

> **配置文件由某个正在运行的进程托管时，不要直接编辑它。**
> 那个进程内存里有一份状态，退出或保存时会把内存写回磁盘，**盖掉你的手工修改**。

## 案例：fcitx5 的 profile

`~/.config/fcitx5/profile` 是纯文本，看起来随手 `vim` 一改就行。但 `fcitx5` 守护进程正跑着，文件在它手里。直接改 → 它一保存就还原了。

**正确做法有两条：**

**A. 通过它提供的接口改**（推荐）
```bash
fcitx5-config-qt        # GUI 改完，由 fcitx5 自己写盘
```

**B. 先停掉进程再改**
```bash
fcitx5-remote -e                                    # 1. 让 daemon 退出
sed -i 's/旧值/新值/g' ~/.config/fcitx5/profile      # 2. 改文件
fcitx5 -d                                           # 3. 重新拉起（-d = daemon）
```

## 改之前先存快照

```bash
cp ~/.config/xxx/conf ~/.config/xxx/conf.bak
# ...改...
diff ~/.config/xxx/conf.bak ~/.config/xxx/conf
```

**`diff` 这一步别跳过**，它是整个练习最有价值的部分：你会看到 GUI 上点的每一下，最终都落成文本文件里的几行改动。

## 为什么这件事在 Linux 上成立，在 Windows 上不成立

| | Windows | Linux |
|---|---|---|
| 配置存哪 | 注册表（二进制黑盒） | 纯文本文件 |
| 唯一入口 | GUI | GUI **只是文本文件的一层皮** |
| 能否 diff | 不能 | 能 |
| 能否 git 管 | 不能 | 能 |
| 能否拷到另一台机器 | 难 | 直接拷 |

**GUI 只是皮** —— 这个认知贯穿整个 Linux 使用：
- fcitx5 配置 → `~/.config/fcitx5/`
- GNOME 设置 → dconf 数据库，命令行入口是 `gsettings`
- CLion 的 toolchain 配置 → `~/.config/JetBrains/`
- 后面会遇到的：udev 规则、CMake toolchain file、systemd unit

全是同一件事的不同马甲。

## 相关工具

```bash
gsettings get  org.gnome.desktop.interface text-scaling-factor   # 读
gsettings set  org.gnome.desktop.interface text-scaling-factor 1.5  # 写
gsettings reset org.gnome.desktop.interface text-scaling-factor  # 还原默认
```

`gsettings` 本质是读写 GNOME 的 **dconf** 数据库 —— 又一个「GUI 是皮」的例子。

## 判断一个配置文件有没有「主人」

```bash
pgrep -a 进程名                 # 这个程序在跑吗
lsof ~/.config/xxx/conf        # 谁打开着这个文件（需装 lsof）
```

没有主人的配置文件（比如 `~/.bashrc`、`/etc/fonts/conf.d/`）随便改，改完新开一个 shell 或重启相关服务即可。
