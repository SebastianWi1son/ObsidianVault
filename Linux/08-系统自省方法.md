# 系统自省方法（不猜，去问系统要证据）

Linux 的核心性质：**系统状态被暴露成可查询的接口，而不是藏在实现里。**

不是「知道所有答案」，而是**知道去问谁**。下面是按「你想知道什么」组织的问法。

---

## 我想知道：这个软件是什么，装了什么

```bash
dpkg -l | grep 关键字            # 已装的包
dpkg -L 包名                     # 这个包装了哪些文件
dpkg -S /某个/文件               # 这个文件属于哪个包
apt-cache policy 包名            # 仓库里有哪个版本
apt-mark showmanual              # 我主动装的（区别于被拖进来的依赖）
dpkg-deb -I xxx.deb              # ★ 装之前先看包的元信息和依赖
dpkg-deb -c xxx.deb              # 装之前先看它要铺哪些文件
```
详见 [[01-deb与包管理]]

## 我想知道：现在跑着什么，它在干什么

```bash
pgrep -a 名字                    # 进程及其完整命令行
ps -p PID -o comm=,args=
ls -l /proc/PID/fd               # 它打开了哪些文件/socket
ls -l /proc/PID/cwd /proc/PID/exe
cat /proc/PID/environ | tr '\0' '\n'   # 它的环境变量（排查"终端能跑快捷键不能跑"神器)
lsof -p PID                      # 需装 lsof
```

**`/proc` 是内核状态的文件系统投影** —— 每个进程的一切都是可读的文件。

## 我想知道：服务活着吗，它说了什么

```bash
systemctl --user list-units --all | grep 关键字     # 用户级服务
systemctl status 服务名                             # 系统级
journalctl --user -f -u 服务A -u 服务B              # ★ 实时跟随日志，-f = follow
journalctl -b -p err                                # 本次开机以来的错误
journalctl --since "10 min ago"
```

**排查任何"某功能不工作"，第一步永远是挂上相关服务的日志再复现一次。** 一条确切的报错胜过一小时试错。

## 我想知道：这个服务到底提供什么能力（D-Bus）

桌面环境的组件之间几乎全靠 D-Bus 通信，而且**接口是自描述的**：

```bash
gdbus introspect --session --dest 服务名 --object-path /对象/路径
gdbus call --session --dest ... --object-path ... --method 接口.方法 参数...
busctl --user list                  # 会话总线上都有谁
```

这等于**把一个闭源 GUI 程序的能力清单直接读出来**。本次实战：从 `org.gnome.Shell.Screenshot` 里挖出 `SelectArea` 这个 GNOME 已经不在 UI 里暴露、但接口仍在的方法（见 [[06-Wayland截图与portal]]）。

## 我想知道：配置的真实值是什么

```bash
gsettings get  组.路径 键          # GNOME / dconf
gsettings set  组.路径 键 值
gsettings reset 组.路径 键
dconf dump /                       # 整棵配置树
cat ~/.config/应用/配置文件         # 大多数应用就是纯文本
diff 配置.bak 配置                  # ★ 改前存快照，改后 diff
```
注意配置文件的归属权问题，见 [[02-配置文件的归属权]]

## 我想知道：硬件和内核（嵌入式开发会天天用）

```bash
lspci / lsusb / lsusb -t           # PCI / USB 设备与拓扑
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT
dmesg -w                           # ★ 实时看内核日志，插拔设备时开着
udevadm monitor --udev --property  # ★ 实时看 udev 事件
udevadm info -a -n /dev/ttyACM0    # ★ 看设备所有可用于写规则的属性
ls -l /dev/serial/by-id/           # 稳定的设备软链名
cat /sys/class/.../某属性           # sysfs：内核对象的文件系统投影
```

## 我想知道：显示 / 会话环境

```bash
echo $XDG_SESSION_TYPE             # wayland / x11
xrandr | grep ' connected'         # 逻辑分辨率 + 物理尺寸（逻辑≠面板 → 正在缩放）
xlsclients -l                      # 谁还在 XWayland 上
loginctl show-session $(loginctl | awk '/wilson/{print $1}')
```

## 通用套路

```
现象模糊
  → 挂日志复现，拿到【确切报错】        journalctl -f -u ...
  → 摸清相关接口到底提供什么             gdbus introspect / --help / man
  → 读出【实际状态】验证假设             gsettings get / Lookup / cat /proc/...
  → 提出假设 → 改一个变量 → 验证         一次只动一个
  → 假设被证伪也是结论（排除了一种可能）
  → 收敛到根因，或确认是架构性约束 → 换路
```

**一次只动一个变量**，否则修好了也不知道是哪条起的作用。

## 诚实的边界

系统不是全透明的：

- **编译进二进制 / 资源包的逻辑照样是黑盒**。本次尝试挖 gnome-shell 的截图调用方白名单就失败了 —— JS 被编进了 gresource，`strings` 挖不到。最后靠**行为观察**（`FlashArea` 被拒 + `gnome-screenshot` 能用）反推出结论。
- **「能查」≠「好查」**。真正的门槛不是权限，是**知道该去问哪个子系统**。这份笔记就是在攒这个索引。
- 查到的是**当下状态**，不是设计意图。为什么这么设计，还得看文档和源码。

## 为什么这件事在嵌入式开发里特别值钱

后面 Stage 5 调 CMSIS-DAP 时，「烧录器连不上」会被拆成一串可查的问题：

```
内核枚举到设备了吗          → dmesg -w / lsusb
创建 /dev 节点了吗           → ls -l /dev/ttyACM* + udevadm monitor
节点权限对吗，我在组里吗      → ls -l + id
udev 规则匹配上了吗          → udevadm info -a -n ...
OpenOCD 到底在哪一步失败      → openocd -d3
```

**每一步都有确切答案可查，没有一步需要猜。** 这是 Linux 做嵌入式开发相比 Windows 最大的优势 —— 不是工具更好，是**系统愿意告诉你它在干什么**。
