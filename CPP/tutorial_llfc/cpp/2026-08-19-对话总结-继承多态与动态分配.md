## 二、std::unique_ptr 事实

- 独占所有权的 RAII 指针包装；离开作用域自动 delete 被管理对象
- 不可复制（编译期禁止），只能 move 转移所有权
- `sizeof(unique_ptr<T>) == sizeof(T*)`，零额外开销；无引用计数（区别于 shared_ptr）
- `std::make_unique<T>()` = `new T()` + 异常安全
- 不依赖异常机制（`-fno-exceptions` 下析构照常执行）；不需要 RTTI；支持自定义释放器（如内存池回收）
- 使用前提：环境有堆、代码本来在用 new/delete

## 三、new/delete 底层（两段式）

- `new Car()` = ① `operator new` 分配内存（底层 malloc）② 在内存上调用 Car 构造函数（写入 vptr）
- `delete p` = ① 调用析构函数（虚则经 vtable 路由：`~Car` → 成员析构 → `~Vehicle`）② `operator delete`（底层 free）归还内存
- 手动修正版：`delete` 后置 `nullptr` 防悬垂
- 手动写法的问题：中途 return / 异常路径会跳过 delete → 泄漏；unique_ptr 把 delete 搬进自己的析构，由编译器保证执行

## 四、嵌入式堆的事实

- STM32F103（Keil）：启动文件 `startup_xxx.s` 中 `Heap_Size EQU 0x200`（默认 512 字节），可改
- MSPM0G7（TI GCC/Clang 工程）：链接脚本划有堆区，默认偏小，需调大
- 8051：Keil C51 无 C++ 运行时，无 new/delete；但可用 `init_mempool` 手动给 malloc 划内存
- 有堆 ≠ 能用 new/delete：还需 C++ 运行时提供 `operator new`（如 newlib-nano）
- FreeRTOS 自带独立堆（`pvPortMalloc` / heap_4.c），与 C 库堆是两套系统
- MCU 工程主流做法：启动时静态分配 / 内存池；实时路径禁用 malloc/free（耗时不确定）；动态分配需内存预算封顶

## 五、拷贝语义澄清

- unique_ptr 不可复制是"所有权"问题（复制会导致 double delete），与深浅拷贝无关
- 浅拷贝：两个指针指向同一块内存，互相干涉，双删风险；含裸指针类的默认拷贝/赋值就是浅拷贝（Rule of Three）
- 深拷贝：读原对象数据、在新内存复制，不干涉原对象
- 深拷贝由被管理类自己的拷贝构造/拷贝赋值实现，unique_ptr 不负责克隆

## 六、嵌入式多态三场景（代码示例）

- **作死**：① 中断/实时路径里 new（分配时间不确定）② 频繁造删不同大小对象（碎片化，最终 malloc 失败）③ 中途 return 路径漏 delete
- **标准（零堆）**：静态实例 + 基类指针数组（多态不需要堆，指针指向成员/全局对象即可）；对象池（`std::array` 预建 N 槽 + 空闲标记，O(1) acquire/release，上限封死）
- **极端必须动态**：数量由外部决定（如 TCP 连接数）；对象生命周期跨作用域（事件投递到其他任务）；跑 Linux 的板子（内存充裕，动态分配是常态）
- 边界：数量/生命周期编译期可知 → 静态；运行期可知但有硬上限 → 池；无上限 → 堆

## 七、课件后半节审查结论（3 处课件错误 + 1 个重点）

- **错误 1（5.3 执行结果）**：课件表格最后一行写 "Show from Base"，实际运行输出是 "Show from Derived"（`show` 是虚函数，基类指针调用仍走 vtable 派发到 Derived 版；已编译验证）
- **错误 2（练习 3 示例输出）**：课件示例输出 "5 6 6"；实际 `add(2, 3)` 编译报错——`AdvancedCalculator::add(int,int,int)` 隐藏基类整组 `add` 重载（已编译验证）；需 `using Calculator::add;` 恢复
- **重点（第 6 节拷贝控制）**：
  - 编译器默认生成的拷贝构造会自动调基类拷贝构造
  - 一旦手写拷贝构造，必须显式写 `: Base(o)`，否则基类部分走默认构造，静默丢数据（不报错）
  - 手写拷贝赋值必须在函数体内调 `Base::operator=(o)`，否则基类部分不更新
  - 打印顺序事实：拷贝构造 = Base copy ctor → Derived copy ctor（初始化列表先跑）；拷贝赋值 = Derived copy assign → Base copy assign（函数体先跑，基类赋值是函数体内手动语句）
- **切片（第 7 节）**：`vector<Base>` 存的是拷贝，派生部分被切掉且 vptr 指向基类 vtable，虚调用回到基类版；修复 = 容器存指针（`vector<unique_ptr<Base>>`），与堆无关，只与"存值还是存指针"有关

## 八、后半节重讲要点（三章）

- 第一章 同名函数：内层作用域遮外层；对象调用就近；基类指针调用分两条规则（非虚按指针类型、虚按对象实际类型走 vtable）；口诀"重载在类内、重写靠 virtual+同签名、其余是隐藏"
- 第二章 拷贝控制：默认生成会接基类；手写后必须自己接（拷贝构造 `: Base(o)`，赋值 `Base::operator=(o)`）
- 第三章 切片：存值必切，存指针不切

## 九、用户最后的理解陈述与确认结果

用户陈述：

1. "只要 base virtual 明确了，就不会有任何歧义和管理成本，override 就明确怎么调都是 derived 自己的实现"
2. "没有 virtual，作用域覆盖会出问题：显式点名调用可以，但对象直接调用和指针调用两种结果不一样，难管理，应该消除"
3. "同名不同参数时不只是调用谁的问题，而是破坏函数原本清晰的语义（存在两层语义在不同情况触发且不告知），会误导人"

确认结果：

1. 基本成立，两个精确化：
   - 例外：构造/析构函数**内部**调用虚函数不派发到派生版（vptr 在构造/析构期间指向当前类的 vtable）
   - virtual 保护的是**签名**不是**名字**：同名不同参时，即使基类标 virtual，派生类定义不同签名同名函数仍隐藏基类整组同名函数；但基类指针调用被重写的同签名虚函数仍走多态
   - "零管理成本"在歧义层面成立；性能上有代价（每对象 +8 字节 vptr、间接调用、不可内联），这是性能成本不是歧义
2. 完全正确：非虚同名函数 `d.f()` 走 Derived 版、`bp->f()` 走 Base 版，同一名字两条调用路径两个结果；`Base::f()` 显式点名是补救手段而非默认行为
3. 正确：隐藏改的是派生类 API 表面——基类整组重载消失（原本合法的调用直接编译失败）；同名函数语义不同时，使用者按名字理解会踩错；接口语义被静默改写

一句话收束：**virtual + 同签名把"名字-语义"绑定关系固化并交给编译器管理；隐藏则让同一个名字在不同调用路径下语义漂移且无人宣告。前者值得用，后者要消除或显式点名。**

## 十、课程评论区讨论：析构 / delete / free 的关系与虚析构的存在理由

- **误区澄清**：`delete Base*` 释放的是整块 `sizeof(Derived)` 内存——`free` 按分配时的块整块归还，与指针类型无关，不存在"只释放基类部分"；漏的从来不是对象空间，而是派生类持有的资源（析构链不完整导致）
- **标准层面**：析构非虚时通过基类指针 delete 是未定义行为；多数编译器实际表现为"内存整块释放 + 析构链不完整"，但不能依赖
- **比喻模型**：内存 = 地，对象 = 房子，构造 = 盖房（初始化成员/获取资源），析构 = 拆房（释放资源），`free`/`operator delete` = 还地（无脑整块还，不看类型）
- `new Car()` = ① 申请 sizeof(Car) 的地（malloc）② 按 Car 的说明书盖房（构造）；`delete p` = ① 按说明书拆房（析构）② 还地（free）；顺序不能反
- **虚析构 = 让"选哪本拆房说明书"在指针类型 ≠ 实际类型时走 vtable 按实际对象选**；非虚时按指针类型猜 → 拆错房（派生析构及成员析构被跳过）
- 派生类说明书必然不同：先拆自己多出来的家具（成员/资源），再让基类拆自己的
- 没有虚函数就不需要虚析构：虚析构只服务于"通过基类指针删派生对象"这一个场景（前提是多态）；没有多态就不会有这种用法，说明书永远选得对
- **用户理解确认**：① 非虚 = 歧义/拆错房 ✅ ② 析构 = 拆房步骤 ✅ ③ 派生类比基类内容多、说明书不同 ✅ ④ 精确化："不要地建房就不需要拆房"应改为"不需要手动拆房（delete），拆错房的问题不会发生"——栈上/静态对象析构照常执行（成员资源照常释放），只是编译器按完整类型自动安排，无 delete 基类指针这回事

## 十一、new vs 直接声明（嵌入式怎么用 class）

```cpp
Car car;                     // 直接声明（栈上）：进作用域盖房，出作用域自动拆
static Car car;              // 静态：程序启动盖房，程序结束自动拆
Car fleet[4];                // 数组：数量写死在固件里
class Controller { Car motor_; };   // 成员：随宿主对象盖/拆

Car* p = new Car();          // 堆：运行期才盖房，数量/时机运行期决定
delete p;                    // 必须手动拆；忘了拆 = 资源泄漏
```

| | 直接声明 | `new` |
|---|---|---|
| 谁分配 | 编译器（编译/链接期定址） | 运行期堆管理（malloc） |
| 何时盖房 | 进作用域 / 程序启动 | `new` 那一刻 |
| 何时拆房 | 出作用域自动拆（编译器保证） | 手动 delete（或 unique_ptr 代劳） |
| 会不会漏 | 不可能漏 | 可能漏（忘了 delete） |
| 数量 | 写死（编译期知道） | 运行期决定，可以变 |
| 开销 | 零（无堆管理） | 堆管理开销 + 碎片 + 时间不确定 |
| 适用 | 数量、时机编译期就知道 | 运行期才知道要几个、活多久 |

**嵌入式规则：默认全部"直接声明"；`new` 只在"运行期才知道数量/生命周期"时用，且必须封顶（对象池）。**

- 数量编译期可知 → 直接声明（成员对象/静态/数组），基类指针指向它们，多态照用，零堆
- 运行期可知但有上限 → 直接声明数组/池（`std::array<Session, 8>`），自己管理空闲槽
- 数量无上限、生命周期跨任务（PC 端/复杂动态场景）→ 才轮到 `new` + unique_ptr
- class、继承、多态、虚析构全部可以在零堆下用满；**堆不是类的前置条件**
