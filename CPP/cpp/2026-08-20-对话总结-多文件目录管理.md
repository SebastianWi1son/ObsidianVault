# 对话总结：多类项目的 .h/.cpp 目录管理（2026-08-20）

> 纯事实总结，不含推断。涉及文件：
> - 练习工程：`/home/wilson/Dev/Workspace/cpp_tutorial/d12-23-memory_manage/`（inc/ 3 个头文件、src/ 3 个 cpp + main.cpp，CMake C++17，单 app target）
> - 现状：`inc/` 平铺 MyClass.h / DynamicArr.h / MemPool.h；`src/` 平铺对应 cpp；`target_include_directories(app PRIVATE ${PROJECT_SOURCE_DIR}/inc)`

## 一、结论

- 当前 inc/ + src/ 平铺结构对 ≤10 个类的学习项目**完全够用**，不是错误
- 企业项目不这么做的原因：规模不同（几百上千个类），平铺会导致找文件靠翻、重名靠猜、模块边界靠脑补
- 真实项目（Chromium、Qt、Boost、Abseil）普遍**按功能模块组织，而非按 .h/.cpp 后缀分类**

## 二、企业三种主流做法

### 1. 按模块分目录（Qt / Boost / 多数企业）

```
project/
├── CMakeLists.txt
├── include/myproj/          # 对外公开 API（可安装）
│   ├── core/
│   │   └── memory_pool.h
│   └── net/
│       └── connection.h
└── src/
    ├── core/                # 模块内部实现
    │   ├── memory_pool.cpp
    │   └── internal/        # 私有头文件，不对外
    │       └── arena_impl.h
    └── net/
        └── connection.cpp
```

模块内部再演化：`模块目录/include` + `模块目录/src`，每模块一个 CMake target，`target_include_directories` 只暴露该模块公开头。

### 2. Google 系（Abseil / Chromium）：头文件放源文件旁边

```
absl/
├── strings/
│   ├── string_view.h
│   ├── string_view.cc
│   └── str_cat.cc
```

好处：头文件和实现永远同屏；同目录头文件编译器自动能找到，include 路径简单。

### 3. LLVM 系：include/ + lib/ 镜像子目录

`include/llvm/CodeGen/` + `lib/CodeGen/`。本质同方案 1，只是公开 API 单独抽出——适合对外发布、需要安装头文件/控制 ABI 稳定的库项目。

## 三、关键原则（比目录形式更重要）

| 原则 | 当前做法 | 企业做法 |
|---|---|---|
| 文件名 = 类名，一文件一类 | ✅ | 保持 |
| 头文件自包含（可独立编译） | ✅ | 保持 |
| `#pragma once` | ✅ | 保持 |
| include 带模块前缀防重名 | `#include "MyClass.h"` | `#include "core/memory_pool.h"` |
| 公开头 / 私有头分离 | 无 | 大模块才需要，`internal/` 目录 |
| 每模块独立编译单元 | 单 app target | 模块化 CMake target（静态库） |

## 五、配套的三个变化

### 1. include 写法带模块前缀

```cpp
// main.cpp
#include <mem/mem_pool.h>        // 从 inc 根开始找
#include <container/dynamic_arr.h>
#include <util/logger.h>
```

CMake 已把 `target_include_directories` 指向 inc，所以直接写即可；模块前缀保证不同库的同名头永不撞名。

### 2. CMake 按模块拆 target

```cmake
# 顶层 CMakeLists.txt
add_subdirectory(src/mem)
add_subdirectory(src/container)
add_subdirectory(src/util)
add_subdirectory(src/core)

add_executable(app src/main.cpp)
target_link_libraries(app PRIVATE core util container mem)
```

```cmake
# src/mem/CMakeLists.txt —— 每个模块一份
add_library(mem STATIC
        mem_pool.cpp
        allocator.cpp
        arena.cpp
        obj_pool.cpp
)
target_include_directories(mem PUBLIC ${PROJECT_SOURCE_DIR}/inc)
```

好处：mem 模块改动只重编 mem；模块可整体拷走去别的项目复用。

### 3. 依赖链 = 模块依赖图

`target_link_libraries` 的链接顺序就是模块依赖图：mem 被 container 用、util 谁都能用、core 只依赖 util。比人脑记"这个头能不能 include 那个"可靠。

## 六、什么时候该拆

| 规模 | 结构 |
|---|---|
| ≤ 10 个类（当前） | 平铺 inc/ + src/，够用 |
| 10~30 个类，有明显功能分区 | 拆 `inc/模块/` + `src/模块/`，单 app target |
| > 30 个类 / 多可执行文件 / 对外发布 | 每模块独立 CMake target + tests/ + third_party/ |

**拆的信号**：在 src/ 里找 MemPool.cpp 要翻好几屏，或 inc/ 里两个类名字相近分不清归属。

## 七、值得从现在养成的两个习惯

1. **目录结构跟着"模块"走，不跟着 .h/.cpp 后缀走**——后缀是编译器的分类，模块是人的分类，人的分类优先
2. **`internal/` 私有头目录**：凡是 MemPool 内部辅助结构（如块链表节点），头文件放 `src/mem/internal/` 而不进 inc/——外部不该 include 它
3. 头文件里只放必要的 include，别把 cpp 的依赖漏进头文件
